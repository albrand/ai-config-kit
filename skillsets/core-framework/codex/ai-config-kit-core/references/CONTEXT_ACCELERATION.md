# Context Acceleration

Optional directives for teams that adopt a generated context accelerator - a
Graphify-compatible knowledge graph / context map or an OpenWiki-compatible
generated agent wiki - so an agent can orient, scope, and discover business
rules faster than raw broad grep. This file is an opt-in capability layer, not
a default dependency and not a source of truth.

Compatible tool classes (vendor-neutral): knowledge-graph / context map
generators that emit queryable nodes and edges, and agent-wiki generators that
emit quickstart, source-map, and update-metadata documents. Name a specific
tool only where the team has already chosen it.

## Core Principle

A context accelerator is an advisory orientation layer. It can make broad
orientation, scope mapping, blast-radius estimation, and business-rule discovery
cheaper when its artifacts are fresh and trusted. It does not outrank source
files, tickets, board state, tests, runtime, config, accepted criteria, or the
framework source-of-truth order.

If the team has chosen an accelerator, the agent must use it at its full useful
power - check availability, freshness, scope, and supported modes, then use the
strongest useful calls - not glance at it and then raw-grep. If no accelerator
is chosen, ignore this file and use normal progressive disclosure.

## Operator Documentation Package

Adopting a context accelerator also requires rich repo-local documentation for
humans and agents. The generated graph, wiki, or index is not enough by itself;
the team must be able to understand how to use it, refresh it, validate it, and
interpret its limits.

The documentation package should cover:

- Purpose and coverage: why this accelerator exists, what repos, paths,
  languages, docs, schemas, tickets, or diagrams it covers, and what it
  excludes.
- Artifact map: local artifact paths, generated wiki roots, graph metadata,
  update metadata, MCP endpoints, reports, and ignored output paths.
- How to use it: concrete graph queries, path/explain/report examples, wiki
  navigation examples, source-map usage, prompt examples, and expected output
  shapes.
- Vocabulary: graph node and edge types, labels, confidence semantics,
  inferred or semantic edge markers, wiki page taxonomy, and symbol/index
  meaning.
- Common workflows: orientation, scope mapping, blast-radius analysis,
  business-rule discovery, dependency tracing, review hot spots, and delegation
  brief creation.
- Refresh and freshness: commands, source revision metadata, update cadence,
  stale-artifact symptoms, rebuild permissions, and what to do when generation
  fails.
- Privacy and artifact policy: secret exclusion, ignore policy, local versus
  committed artifacts, CI opt-in, and private endpoint handling.
- Verification boundary: which claims are advisory, what must be checked
  against source files, tickets or board state, tests, runtime, config, and
  accepted criteria.
- Troubleshooting: common empty, stale, partial, noisy, or misleading graph/wiki
  states and the fallback path.
- Token impact: measured savings when available, vendor-reported claims when
  not locally measured, maintenance cost, and when direct source reads are
  cheaper.

If this documentation package is missing, stale, or too thin to operate the
tool confidently, record the accelerator as `limited` or `blocked` even if the
raw generated artifact exists. A barely understandable graph or wiki is not an
adopted capability.

## Capability And Freshness Gate

Before relying on an accelerator, check:

- Artifact availability: graph or wiki present and readable for this repo.
- Operator documentation: repo-local docs explain usage, vocabulary,
  workflows, refresh, privacy, verification, troubleshooting, and token impact.
- Freshness: generated against a recent source state; update metadata recorded.
- Scope: covers the relevant paths, modules, and languages; ignore out-of-scope
  regions.
- Supported modes: which query, path, explain, summary, report, or MCP calls
  the accelerator exposes; which wiki quickstart, source-map, or metadata calls
  exist.
- Trust: generated by an authorized run, with secret exclusion and ignore
  policy applied.

If the artifact is stale, missing, partial, or untrusted, rebuild or update it
when the team allows; otherwise fall back to normal progressive disclosure
(indexes, file lists, metadata, focused `rg`) and state the gap explicitly in
the plan and close-out. Never silently treat a missing accelerator as "nothing
useful here".

## Operating Modes

When an accelerator is available and trusted, prefer it for the first pass of:

- Broad orientation: what the repo does, entry points, major modules.
- Scope mapping: which files and modules a change touches.
- Blast radius: callers, dependents, reverse dependencies, config consumers.
- Business-rule discovery: where a rule lives, which entities it spans, and the
  tickets or docs that back it.

Use the strongest useful calls the accelerator supports:

- Graph: query, path, explain, summary, report, or MCP-backed lookups.
- Wiki: quickstart, source maps, update metadata, and linked page navigation.

After orientation, drop to normal source reading, `rg`, tests, and runtime
evidence for the load-bearing detail. The accelerator points; the source
decides.

## Advisory, Not Authoritative

Generated graph and wiki claims are advisory, never authoritative.

- Verify every load-bearing claim against source files, tickets or board,
  tests, runtime, config, and accepted task criteria before acting on it.
- Treat inferred or semantic edges and wiki summaries as hypotheses. The agent
  must label inferred or semantic content as such when reporting it.
- Do not let the accelerator override the framework source-of-truth order, the
  challenge loop, or validation gates.
- When an accelerator claim and a source file conflict, the source file wins
  unless the source is itself superseded by higher-authority evidence.

## Privacy And Security

Accelerator artifacts can concentrate sensitive information. Apply:

- Secret exclusion: scan and strip secrets, credentials, and tokens before
  generation; enforce an ignore policy for secret-bearing paths.
- Ignore policy: exclude secrets, private URLs, private account identifiers,
  and closed-scope details from the graph and wiki.
- Opt-in for heavy indexing: no semantic document/media indexing, embeddings,
  or model-backed indexing without explicit team opt-in.
- Opt-in for CI: no accelerator generation or indexing in CI without explicit
  opt-in and a documented credentials boundary.
- Instruction mutation review: generated-wiki tools that update `AGENTS.md`,
  `CLAUDE.md`, or other instruction files require explicit team opt-in and
  review of instruction precedence before their changes are accepted.
- No private URLs or secrets in shared framework files; accelerator config that
  names private endpoints stays repo-local.

## Artifact Policy

- Local by default: generated graphs and wikis are local, gitignored artifacts
  unless the team decides otherwise.
- Commit only after team review and only content that passes the privacy and
  secret checks above.
- Commit the operator documentation package when it contains no closed-scope
  details; keep private endpoints, credentials, and customer-specific examples
  in repo-local ignored files.
- Treat committed accelerator artifacts as build outputs, not source of truth;
  regenerate from current source on demand.

## Integration With The Framework

- Load this file only when the team uses a context accelerator; it is not part
  of the Minimum or Implementation profile by default.
- Record accelerator availability and freshness in the harness capability
  record (`FRAMEWORK_MANIFEST.md`, `TEMPLATES.md`) as `available`, `limited`,
  `blocked`, `unavailable`, or `unknown`, with freshness in the evidence field.
- Record whether the operator documentation package exists and whether it is
  sufficient to use the chosen tool without rediscovering basics from scratch.
- Route accelerator lookups as scoped capabilities under the external-tool and
  MCP routing rules (`HARNESS_STRATEGY.md`).
- Use progressive disclosure and deterministic pre-processing first
  (`TOKEN_ECONOMY.md`); the accelerator is a faster path to the same
  orientation, not a replacement for source evidence.
- Keep accelerator assumptions challengeable evidence under
  `DIRECTIVE_CHALLENGE_AND_CAUSAL_INFERENCE.md`.

## Anti-Patterns

- Treating generated graph or wiki claims as authoritative.
- Acting on inferred or semantic edges without labeling them as inferred.
- Skipping the freshness gate and using a stale artifact for load-bearing
  decisions.
- Running semantic, media, or model-backed indexing or CI generation without
  explicit opt-in.
- Committing accelerator artifacts with secrets, private URLs, or closed-scope
  details.
- Forcing the accelerator as a default dependency when the team has not adopted
  one.
- Shipping a graph or wiki with no practical documentation for queries,
  vocabulary, refresh, verification, or troubleshooting.
- Letting the accelerator replace `rg`, source reading, tests, or runtime
  evidence for the actual change.
